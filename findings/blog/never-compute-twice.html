01The question

Most speedups for small language models trade something away: a smaller quantization, a shorter context, a drafter that sometimes changes the answer. We asked the opposite question.

On a fixed edge board, with a fixed model and fixed prompts, how much speed and energy is left on the table if the output must stay exactly the same, byte for byte? If the answer is "a lot", every deployment gets it for free: nothing has to be re-validated, because nothing the user sees has changed.

The answer turned out to be: about a fifth to a third of the time and energy, depending on the model. The engine that gets there is CoPR, two exact techniques added to the little-gemma runtime. It never computes the same thing twice: not the shared few-shot prefix, and not tokens it can copy from the prompt and check in one batched pass.

02How it was measured

Every number on this page comes from raw runs committed to the repository, and one script rebuilds all of the paper's tables from them.

Workload
MMLU-Pro, 300 questions per model (three stratified subsets of 100), 5-shot chain of thought, greedy decoding, thinking off.
Models
Gemma 4 E2B and E4B, Unsloth Q4_K_XL QAT GGUFs (MLX 4-bit builds of the same checkpoints on the iPhone).
Hardware
NVIDIA Jetson Orin Nano 8 GB at 15 W for the engine comparison. Raspberry Pi 5 (CPU only) and iPhone 15 Pro for deployment context.
Baselines
llama.cpp, llama.cpp with its own n-gram drafting (width 4, not exact), and little-gemma, the runtime CoPR builds on.
Proposed
CoPR = little-gemma + prompt-lookup drafting through its batched verify (width 3) + shared-prefix KV reuse made exact for sliding-window ring buffers.
Energy
Board DC draw from the Jetson's INA3221 rails (the Pi's PMIC on the Pi), integrated over the working window and divided by generated tokens. Not wall power.
Exactness
Reply text compared byte for byte, per question, against the same engine with every switch off.

03Where the time goes

Before optimizing anything we took the baseline apart. Two things stood out. First, almost all of a request is decode: the model writes about 660 tokens of reasoning per question, and prefill is only around 3% of the time. Second, little-gemma re-prefilled the whole 5-shot prompt every question: 1,444 prompt tokens against llama.cpp's 381, because llama.cpp already reuses the shared prefix.

So the target is clear. Prefix reuse can only win back a few percent of time, but it is worth doing because it is free and exact. The real lever is decode: fewer forward passes per generated token.

04Two exact tricks

Prompt lookup. A chain-of-thought reply to a multiple-choice question repeats the question constantly: option text, units, names. When the last tokens written also appear in the prompt, the tokens that followed them there are a cheap guess for what comes next. CoPR drafts those tokens and checks them in one batched forward pass. Greedy decoding keeps a drafted token only if the model would have picked it anyway, so the reply cannot change; a wrong guess just costs a slightly wider pass.

Prefix reuse. All 300 questions share the same 5-shot preamble. Reusing its KV cache is standard in llama.cpp, but Gemma 4 interleaves sliding-window layers whose cache is a ring buffer, and naive reuse there silently corrupts state once the window wraps. CoPR snapshots the ring buffers at the prefix boundary and restores them exactly, so prompt tokens processed per question drop from 1,444 to 385 with no change in output.

The rule we held ourselves toA technique only counts if every one of the 600 replies (300 per model) is byte-identical to little-gemma with the technique off. Anything that drifts, even when accuracy holds, is out.

05Results on the Jetson

Four engines, two models, 300 questions per cell, same board, same weights, same prompts. Toggle the model and the engines to compare.

Against llama.cpp, CoPR cuts wall time per question by 22% on E2B and 34% on E4B, and energy per token by 20% and 30%. It also beats llama.cpp's own n-gram drafting, which is not even exact: only 29 of 300 E2B replies (20 of 300 on E4B) match llama.cpp without drafting. Mean power rises slightly because the GPU is busier, but the request finishes so much sooner that energy falls.

06Take it apart

CoPR is two switches. Turning each one on alone shows what it is worth. Every row below is byte-identical to little-gemma on all 300 questions.

Prompt lookup carries the speed: alone it gives almost all of CoPR's decode gain. Prefix reuse carries the prompt: it removes 73% of the tokens processed per question but, since prefill was only ~3% of the time, buys a couple of seconds at most. Its energy per token reads slightly higher than the baseline because those rows ran after the Jetson's clocks were pinned (+5–9% energy; see section 10). Together they compound to the best wall time on both models.

07Picking the verify width

A wider verify pass confirms more drafted tokens when the guess is right, but every pass gets more expensive. We swept the width on 28 questions (two per subject) before committing to the full 300.

The Pi tells a different story, which is why the width is a per-device setting rather than a constant. On its CPU a batch of 4 tokens costs about the same as a single token (1.06×), because the Q4_0 kernels work on 4-row tiles, while batches of 2 and 3 cost 1.30× and 1.58×. Replaying recorded Pi replies offline shows prompt lookup accepting 1.47–1.51 tokens per pass at width 4 on E2B MMLU-Pro, and 1.39–1.50 across E4B, thinking-on and GSM8K replies.

08Accuracy did not move

CoPR's replies are identical to little-gemma's, so its accuracy is identical by construction. The real question is whether little-gemma differs from llama.cpp. Different kernels flip greedy choices at near-ties, so only 32 of 300 E2B replies match between the two engines, yet the scores are statistically the same.

09Same model, other devices

The same checkpoints and the same 300 questions also ran on a Raspberry Pi 5 (llama.cpp, CPU only) and an iPhone 15 Pro (MLX, in our GemmaBench app). This is deployment context, not an engine comparison: the engines differ, and the iPhone's energy is a battery estimate.

Accuracy is flat across all three devices: every score sits inside the others' 95% interval. What changes is speed. The Jetson with CoPR decodes 4–5× faster than the Pi and roughly 2× faster than a throttled iPhone, at a third of the Pi's energy per token.

10What would change the result?

What we are confident of, what we are not, and what would move the numbers.

  1. Exactness is the strong claim; speed is a single runByte-identity is checked on all 600 replies and cannot be luck. Time and energy come from one run per configuration. A repeat of CoPR on E2B s1 landed at 29.78 vs 29.54 tok/s and 0.404 vs 0.369 J/tok (the repeat ran with clocks pinned, below), so expect a few percent of run-to-run spread, more in energy than in speed.
  2. The Jetson's clocks were pinned mid-studyIn early October the board's clocks were locked, which adds 5–9% to energy. The prefix-reuse ablation rows ran in that window. Compare time, not watt-hours, across it. The manuscript does not yet name this.
  3. Two rounding errata in paper Table IVThe data gives 0.224 and 0.369 where the paper prints 0.225 and 0.370 (rounded twice). The "width 3" n-gram row in that table never drafted at all; it is a plain llama.cpp rerun.
  4. One workloadMMLU-Pro chain of thought copies a lot from its prompt, which is exactly what prompt lookup feeds on. Replays on GSM8K and thinking-on replies still accept 1.34–1.43 tokens per pass at width 3, but tasks that copy little (free-form chat, code from scratch) will gain less.
  5. Separating engine from techniqueSome of the gap to llama.cpp is little-gemma itself (25.58 vs 23.00 tok/s on E2B before any switch). The ablation isolates CoPR's own share: +15% decode on E2B and +17% on E4B over little-gemma.
  6. Where it should do betterMulti-turn agents re-send a growing transcript and tool list every turn. That is more shared prefix to reuse and more prompt text to copy from than single-turn MMLU-Pro offers.

11Reproduce it

Every table in the paper is rebuilt from committed raw runs. It needs Python 3.9 and nothing else: no packages, no network, no board.

git clone https://github.com/rifkyariy/agentic-edge.git
cd agentic-edge
python3 benchmark/paper_tables.py

It prints the paper's value beside the recomputed one, line by line. Re-running the experiments themselves takes about 42 board-hours on a Jetson Orin Nano; the README walks through it, and findings/TABLES.md has every result as a table image.
