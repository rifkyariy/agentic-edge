## What the paper gives, and what we chose

The paper (arXiv 2608.06370 §3.4) released no entry IDs or code, and its description of these two
subsets is thin and partly self-contradictory. Every row below marked *ours* is a deviation to
state in the write-up.

| | Paper | T1 here |
| --- | --- | --- |
| Chaining, size | 52 tasks, length 2–20; 17 of length ≥ 6, 10 of length ≥ 13; no other counts | Same totals: 35 tasks of length 2–5, one each of 6–12, one each of 13–20 plus an extra 15 and 20 (*ours*) |
| Chaining, source | "selected from BFCL v4", categories not named | Synthetic (*ours*): one running quantity (bank balance, warehouse stock, game score, garage occupancy) changed step by step; each call takes the value just before its step. Integers only, so exact scoring is fair |
| Chaining, stubs | Echo the arguments; the model computes intermediate values itself | Same, and every T1 tool description ends "Returns the arguments it was called with." (*ours*, from the pilot) |
| Chaining, JSON | Multi-turn: call, get the result, call again; max turns not stated | Multi-turn loop, echoed arguments as each tool result, up to 25 turns (*ours*) |
| Fan-out, size | 32 enumeration tasks; sizes 7, 9, 11, 13, 15, 20, 30, 48; counts per size not stated | 4 per size, one per template: project status by codename, meeting reminders, warehouse stock, currency conversion (*ours*) |
| Fan-out, source | "a synthetic corpus", not described | Synthetic, invented entity names (*ours*) |
| Code Mode | One script per task | Same (D3a), lenient harness (D12) |
| Scoring | Every required call present with correct arguments; fan-out also reports "did the model issue all N calls" | `pass` as T0; `enum` = every required call issued, arguments aside; reported per chain length band (2–5, 6–12, 13–20) and per fan-out size |
| Output limit | Not stated | 4,096 new tokens for every tier (T0 never reached the old 1,024) |

## Harness changes

* `run.py`: a JSON loop for `multi_turn` tasks. Turn 1 sends `cache_prompt: false`, later turns
  `true` (D8: reuse within a task only). The timeout now covers the whole task (D7, 600 s for now).
  Each turn's timings and start time are kept in `turns`.
* `score.py`: `enum`, and groups `chain_len02-05 / 06-12 / 13-20` and `fanout_nNN`.
* `energy.py`: the same metrics as `main`'s `summarize_run.py`: decode-only power, prefill and
  decode tok/s, J per token (generated, and all tokens), decode tok/s per W, and peak power. With
  `--tasks` it also gives J and seconds per task, pass rate, and passes per Wh for each category
  and group.
* `run_jetson.sh`: `TIER=t0|t1|t1-pilot`, with `-n` and `--max-tokens` at 4096.

## Pilot findings (E4B, 2026-10-30)

The first pilot (`runs/t1-pilot-*-q8_0-off-e4b`, run on the tasks before these fixes) passed all
five checks below and found two problems with the tasks, both fixed before the rerun (`-r2`
folders, 2026-11-01):

* **Invented country names.** JSON refused both `get_population` tasks ("I can only look up the
  population of real countries"), which penalizes JSON for how the task was built. That template now
  asks for the status of internal projects by codename, where invented names are normal.
* **Code Mode never sees what a stub returns.** One 17-step chain script did
  `score = await tools.deduct_points(...)`, so each echoed argument object nested into the next
  call. JSON sees every echo as the tool result, so every T1 tool description now says it returns
  its arguments, giving both interfaces the same information.

The rerun, per task (pass rate, mean seconds, mean J):

| | JSON | Code Mode lenient |
| --- | --- | --- |
| Chains (11) | 11/11, 15 s, 154 J | 10/11, 27 s, 275 J |
| Fan-out (8) | 7/8 (enum 8/8), 47 s, 492 J | 7/8 (enum 8/8), 22 s, 221 J |

* The codename template fixed JSON's refusals: both project-status tasks pass, and fan-out goes
  from 5/8 to 7/8.
* chain_46 still fails in Code Mode with the same script, although the TS API now says each tool
  returns its arguments. That is the model's error, not the task's, so it stays a failure.
* fanout_21 (20 reminders) fails in both interfaces on one misspelled name, as in the first pilot.
* The five checks still hold. The longest task is fanout_31 on JSON at 128 s, so D7's 600 s is
  enough on E4B.

## Pilot (M4), then the runs

On the Jetson, from `~/research/toolcall`, with the voice agent stopped:

```bash
TIER=t1-pilot ./run_jetson.sh e4b
```

```bash
TIER=t1-pilot IFACE=code-lenient ./run_jetson.sh e4b
```

Things to check in the pilot results before the full runs:

1. **The chat template takes `role: tool` messages.** `chain_*` JSON tasks should have more than
   one turn, and the turns should carry on the chain without errors.
2. **Cache reuse works (D8).** In `turns[1:]`, `timings.cache_n` should be above 0 and `prompt_n`
   small. If turn 1 is sent with `cache_prompt: false`, the server might not keep that turn's cache.
3. **The token cap is enough.** On `fanout_31` (48 calls), `finish_reason` should not be `length`.
4. **Timeouts (D7).** The worst-case time is `chain_51` (20 turns) on E4B; set D7 from the pilot.
5. **Energy.** `energy.json` should have `by_group` and `generation_mean_w`, with idle near 5 W.

After the pilot, Stage 1 for T1 is 8 runs (JSON and Code Mode lenient × q8_0 and turbo3 × E2B
and E4B). From T0's speeds that is about 6–8 h of board time:

```bash
TIER=t1 ./run_jetson.sh e2b
```

